# `/history` の表示と確認

`/history pay` は本人の入出金、`/history issue` はサーバーの発行履歴を、
新しい順に5件ずつ表示します。返信は実行者だけに見えます。
発行履歴はサーバーの管理者だけが参照できます。

ミュートした通貨・相手の行は表示しません。件数とページ送りも非表示設定を反映します。
契約の行は参加者・固定支払先・連携Botのミュートも反映します。解除は `/mute list` の
「解除」ボタンから行います。入出金APIにも同じ設定を反映しますが、サーバートークンで
読む発行履歴APIには個人のミュートは適用しません。

表示を隠しても取引や残高は変わりません。取引後残高は実際の保存値をそのまま表示するため、
非表示の行を挟むと、見えている金額だけでは前後の残高がつながらない場合があります。
照合するときは該当するミュートを解除してください。

## 表示項目

| 項目 | 内容 |
| --- | --- |
| 種別・金額・通貨 | 送金、受取、発行、契約にロック、契約から返却、契約から受取、自己送金。入金に `+`、出金に `−` を付け、金額は3桁で区切る |
| 取引後残高 | `/history pay` ではその行を処理した直後の自分の通貨残高。保存されていない過去の履歴は「未記録」 |
| 発行枠残高 | `/history issue` では発行直後のサーバーの発行枠。発行先個人の残高は表示しない |
| 相手 | 送金先・送金元・発行先・発行元・契約のアプリを、種別に応じたラベルで表示 |
| 日時 | Discordのタイムスタンプ。利用者側のタイムゾーンで表示 |
| 取引ID | 送金・契約は `P123`、発行は `I123`。台帳別のIDなので接頭辞まで含めて照合する |
| 契約ID | 契約の記録だけに表示。同じアプリの複数契約を区別できる |
| 一覧の条件 | 通貨と相手、または発行先。指定がないものは「すべて」 |
| 一覧の位置 | 全件数、ページ番号 / 総ページ数、表示範囲。⏪（最初）・⏮️（前へ）・⏭️（次へ）・⏩（最後）で移動 |

金額と種別を先頭で強調し、相手・取引後残高・日時・IDを改行して表示します。
取引間には区切り線を入れます。自己送金は入金・出金の符号を付けず、
「残高変動なし」と表示します。契約へのロックと受取は別々の記録です。
ロックした側の履歴に、契約からの支払いを二重に出金計上しません。

絞り込んで0件になった場合は条件を残し、「指定した条件に一致する履歴はありません」
と表示します。サーバー全体で発行がなかったという意味にはしません。
ページを移動しても条件は維持されます。

Bot未連携の契約アプリは名前とclient IDで識別します。名前内の改行とバッククォートは
無害化し、すべての返信でメンション通知を抑止します。

## 表示できる情報の範囲

請求承諾の支払いも送金・受取として表示します。支払い履歴に請求IDとの関連や
取引メモは保存されていないため、それらを推測して表示しません。
現在の残高確認には `/bal` を使います。

金額はウォレットの移動額です。契約の利用明細すべてを表すものではありません。
取引IDは表示上の識別子で、取引詳細を開くボタンはありません。

## 残高の保存

マイグレーション `0028_history_balances.sql` 適用後、新しい取引から残高を保存します。
送金・請求承諾は送金側と受取側、発行は受取側と発行枠、契約は実際にウォレットが
増減した側の残高を、金銭移動と同じトランザクションで記録します。
ロールバックされた取引の残高記録は残りません。

一括処理は各行の処理順に対応する残高を記録します。自己送金では残高を増減させません。
契約支払いを複数の資金提供者の行に分ける場合も、受取側の残高を各行で加算します。
契約からの支払いでは、預託済みの送金側ウォレットを再び減算しません。

既存行はNULLのまま保持し、現在の残高から遡って補完しません。
新しいコードを利用する前にマイグレーションを適用する必要があります。
旧版の書込処理が作った行も、残高列がNULLなら「未記録」です。
APIでは本人の履歴に `balance_after`、発行履歴に `pool_balance_after` を返します
（整数の文字列、未記録なら `null`）。相手の残高はAPIでも返しません。

履歴の並び順は従来どおり日時、台帳種別、IDです。日時が同じ秒の別台帳の行は、
実際の処理順と表示順が一致しない場合があります。残高は各処理時点の保存値です。

## 応答しない問題の修正

6〜10件の履歴では「次へ」と「最後」が同じページを指し、以前は同じ `custom_id` を
送っていました。末尾側では「最初」と「前へ」も重複していました。
Discordは同一メッセージ内での `custom_id` 重複を許可しません。
ページと条件は維持しつつ、ボタンごとに異なるIDに修正しました。
既存のIDも引き続き読み取れます。

参照: [Discord Component Reference — Custom ID](https://docs.discord.com/developers/components/reference#custom-id)。
ローカルで重複する応答を再現し、回帰テストで検出しています。
一般のJSONスキーマ検証だけではこの重複を検出できませんでした。

## 人間による再確認

テスト環境で修正版が利用可能になった後に確認します。この作業自体ではDiscordへの
コマンド登録・投稿やデプロイを実施しません。

1. テスト環境でマイグレーションと修正版を適用後、入出金と発行を含むアカウントで `/history pay` を開き、金額・相手・日時を探しやすいか確認する。
2. 同じアプリの複数契約について契約IDが異なること、取引IDも照合できることを確認する。
3. 6件以上ある条件を `/history pay unit:<通貨> user:<相手>` に指定し、ページ移動後の条件・件数・表示範囲を確認する。
4. 管理者で `/history issue user:<発行先>` を開き、指定した発行先だけが表示されることを確認する。該当しない相手の0件表示も確認する。
5. 新しい送金・発行・契約操作の直後に、履歴の取引後残高を `/bal` と照合する。既存行の「未記録」と、新しい残高0の表示が区別されることも確認する。
6. デスクトップとモバイルで、5件分の長さ、長いアプリ名・client IDの折り返し、ボタンの分かりやすさを確認する。

最終的な項目の十分性と見やすさは人間が判断します。自動テストは履歴の内容、
表示する項目、絞り込みとページ移動、権限、Discord向けJSONを検証します。
実際のDiscordクライアントの描画はローカルのスキーマ検証だけでは確認できません。
